# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Azure Functions (.NET 10 isolated worker, Flex Consumption/Linux) app that exposes an authenticated dynamic-DNS HTTP endpoint (DynDNS v2) and writes `A`/`AAAA` records to existing Azure DNS zones via the Azure SDK and managed identity. `README.md` is detailed (request flow, response contract, config reference, manual deployment); `docs/deployment-plan.md` and `docs/quick-ops.md` cover deploy/ops.

## Commands

```bash
dotnet build
dotnet test
dotnet test --filter "FullyQualifiedName~AuthServiceTests"        # one test class
dotnet test --filter "FullyQualifiedName~AuthServiceTests.SomeTest" # one test
dotnet publish src/AzureDdns.FunctionApp/AzureDdns.FunctionApp.csproj -c Release -o out/functionapp
```

The function project uses the `Azure.Functions.Sdk` project SDK, which generates an extensions helper project when the function project itself is restored. A solution-level `dotnet build` still works but prints warning AZFW0108; restore `src/AzureDdns.FunctionApp/AzureDdns.FunctionApp.csproj` directly to avoid it (CI does).

Local run: copy `src/AzureDdns.FunctionApp/local.settings.json.example` to `local.settings.json`, set `DNS_SUBSCRIPTION_ID`, `DNS_RESOURCE_GROUP`, `CONFIG_PATH`, then `func start` from the app project folder (it builds into `bin/output`). `AzureWebJobsStorage` can be left empty for a quick HTTP-only check; the host then reports a storage health warning, which is harmless locally.

Post-deploy validation: `scripts/smoke-test-dyndns.ps1`. Infra: `infra/main.bicep` (+ `modules/dns-zone-rbac.bicep`), deployed with `az deployment group create` or `azd` (`azure.yaml`). The runtime version (`functionAppConfig.runtime.version`) is part of the Function App resource, so a runtime change needs the Bicep deployment as well as the zip deploy. Deployment compiles the Bicep on the fly; a compiled `infra/main.json` (from `az bicep build`) is gitignored and should not be committed.

## Architecture

One HTTP function over a protocol-neutral coordinator, over a service layer (`src/AzureDdns.FunctionApp/Services`):

- `Functions/DyndnsUpdateFunction.cs` — `GET /api/nic/update?hostname[&myip]` with HTTP Basic auth (DynDNS v2, for Unifi/ddclient/OpenWRT). It only parses the wire format and maps a `DdnsUpdateStatus` to `good <ip>` (record written) / `nochg <ip>` (already current, no write) / `badauth`/`nohost`/`911` (`911` with HTTP 503 when the config file is unavailable). `nohost` is deliberately returned for both unknown and unauthorized records to avoid leaking zone config. The earlier `/api/update` endpoint (credentials in the query string) was removed; do not reintroduce secrets in URLs.
- `Services/DdnsUpdateCoordinator.cs` — all policy: load config -> authenticate -> resolve hostname -> authorize -> resolve IP -> find zone settings -> write DNS. It returns a `DdnsUpdateResult` with a `DdnsUpdateStatus` and never throws for expected failures (including Azure DNS and managed-identity credential failures). A new API front end should be a thin adapter over `IDdnsUpdateCoordinator`, like the DynDNS function.
- Other services: `AuthService` (SHA-256 key-hash check + per-client zone/record authorization, `*` wildcard record name, `@` for apex; `Authenticate` does the same work whether or not the client exists — full client scan, always hash, always fixed-time compare against a dummy hash when there is nothing real — so response time does not reveal which client names exist. Do not add early returns for unknown clients. Measured unknown/known time ratio went from ~0.03 to ~0.9), `FqdnResolver` (longest-suffix match of FQDN to a configured zone), `IpResolver`, `DnsUpdateService` (Azure DNS SDK; reads the existing record set first and skips the write when it already holds exactly the one desired address and the zone's TTL — `UpdateDnsResult.Changed` — via the pure, unit-tested `DnsRecordComparison.IsCurrent`; a 404 on the read means "create it"), `ConfigProvider` (reads the config file).
- Config is `config/dyndns.json` (zones with TTL; clients with `keyHash` and `allowedRecords`). It is a packaged file by design — changing clients/keys means republishing, not runtime refresh. Typed models are in `config/DyndnsConfig.cs`. `ttl` defaults to 300.
- IP resolution (`IpResolver`) is not just the raw connection address: when the remote address is loopback/private/link-local (i.e. a known proxy hop, as behind Azure's front end), the source IP is taken from `X-Forwarded-For`, then `CLIENT-IP`; otherwise from the connection. An explicit `myip` wins but a mismatch with the source IP is logged. IPv4-mapped IPv6 addresses (`::ffff:a.b.c.d`) are normalized to IPv4 so they write `A`, not a bogus `AAAA`. `AddressPolicy` then refuses addresses that cannot work in public DNS (private/CGNAT/loopback/link-local/multicast/reserved IPv4; anything outside `2000::/3` for IPv6) with `DdnsUpdateStatus.AddressNotPubliclyRoutable` (`911`); the documentation ranges are allowed by default on purpose because `scripts/smoke-test-dyndns.ps1` publishes addresses from them, and refused when `ALLOW_DOCUMENTATION_ADDRESSES=false` (Bicep `allowDocumentationAddresses`; the smoke test then needs `-TestIpv4`/`-TestIpv6`).
- Logging: `Services/IpDiagnosticsLog.cs` logs the IP-resolution summary on every request, and with `LOG_ALL_REQUEST_HEADERS_FOR_IP_DIAGNOSTICS=true` all headers (credential-like ones redacted by name fragment). It must never log the query string. Every request-derived string that reaches a log must go through `LogSanitizer.Sanitize` — CodeQL's `cs/log-forging` check on PRs flags unsanitized ones. Avoid identifiers containing "trusted" (CodeQL's sensitive-data heuristic flags them; that is why it is `KnownProxyHop`).
- A missing, unreadable or malformed config file makes `FileConfigProvider` throw `ConfigurationUnavailableException`; the coordinator logs it and reports `ConfigurationUnavailable` (HTTP 503). A valid-but-empty file (`{}`) is not an error and just fails authentication.
- Zone lookup in config goes through `DyndnsConfig.TryGetZone`, which ignores case, surrounding whitespace and a trailing dot on either side. `AuthService.IsRecordAuthorized` compares `allowedRecords[].zone` the same way (via `DyndnsConfig.NormalizeZoneName`).
- An update touches only the record type matching the IP family (IPv4 → `A`, IPv6 → `AAAA`); the two must stay independent.
- Infra: the Function App is `httpsOnly` and capped at a low `maximumInstanceCount` on purpose (anonymous public endpoint; the cap bounds cost if abused). Storage still uses an account-key connection string for `AzureWebJobsStorage`.
- CI is a single workflow, `.github/workflows/ci.yml`, with three jobs on every pull request (and manual dispatch): `test` builds and runs the tests, `bicep` compiles `infra/main.bicep` with `az bicep build`, and `unifi-client` runs the Unifi client end to end under Python 2.7.18/curl 7.74.0 in a container. It restores the function project directly and then the test project (not the `.slnx`). CodeQL runs separately via GitHub's default setup, and `main` is protected by a ruleset (`Protect main`) requiring a PR plus the `test`, `bicep` and `unifi-client` checks — a new CI job must be added to that ruleset's required checks by name (via `gh api repos/arkane-systems/azure-ddns/rulesets/<id> --method PUT`) once it has run once. Deployment is deliberately manual CLI, not CI (see README). Dependabot (`.github/dependabot.yml`) opens weekly NuGet/Actions update PRs.
- Tests are xUnit (181 passing at last run; `DnsUpdateService` itself calls Azure and has no unit tests — its read/404/skip path was verified once against the real zone with a read-only probe) in `tests/AzureDdns.FunctionApp.Tests`: stub-based unit tests per service, `DdnsUpdateCoordinatorTests` for the pipeline, and `DyndnsUpdateFunctionTests` which exercise the function together with a real coordinator over stub collaborators. No Azure access is needed.
- `unifi-client/` is a separate Python 2 client + systemd units for Unifi gateways (own README); it is not part of the .NET solution (`azure-ddns.slnx`). It calls `/api/nic/update` with Basic auth, feeding `curl` its URL and credentials on stdin so the key never appears in argv.
- **`unifi-client/arkane-ddns-client.py` must stay compatible with Python 2.7.18 and curl 7.74.0** — that is what is available on the client devices (Unifi gateways; the curl version is the same across Unifi Network platforms). No f-strings, no `subprocess.run`, no `text=`/`encoding=` arguments, no `urllib.parse`, no type hints, no Python 3-only libraries; the script uses `ConfigParser`, `urllib.quote` and `str` (bytes) semantics. There is no Python 2 on the dev machine, but WSLC (Docker-compatible; `wslc run`/`wslc pull`) is installed. `scripts/test-unifi-client.sh` runs the whole client end to end in a `debian:bullseye-slim` container (which ships exactly Python 2.7.18 and curl 7.74.0) against a local HTTPS server standing in for the API; only `ip` is faked. See the usage comment at the top of that script; under Git Bash set `MSYS_NO_POSIX_PATHCONV=1 MSYS2_ARG_CONV_EXCL="*"` or `/client` is rewritten to a Windows path. CI runs the same script as the `unifi-client` job. `python scripts/check-py27-compat.py unifi-client/arkane-ddns-client.py` is a quicker static check for Python 3-only syntax and calls. Mind `__pycache__`/`*.pyc` — they are gitignored.

## Conventions

- Keep the DynDNS v2 contract (`/api/nic/update` response bodies and status codes) stable unless requirements change; keep plain-text responses and source-IP fallback when `myip` is omitted.
- Small, testable service classes; the function stays a thin adapter. Strongly typed config; managed identity, no embedded credentials.
- Never log raw client keys, and never put them in URLs.
- Prefer simple deploy-time configuration over runtime-refreshable config.
- Comments/docs should be thorough enough for re-entry after 6–12 months. Keep the README accurate; remove material that no longer describes the system rather than leaving it stale.
- Merge PRs with merge commits (user preference), not squash or rebase.
